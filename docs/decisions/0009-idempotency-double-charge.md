## Decision

When an attempt exceeds its deadline without a response, the engine enters **ambiguity**: it does not know whether the issuer will authorize. The decision is that ambiguity is managed by a **lease**, and the chain runs on **confirmation, not suspicion**:

1. **The lease (the retry state machine).** At most one *unconfirmed* authorization exists per transaction at any time. A dispatch is legal only from a lease-free state; the lease is released only by a **confirmed terminal** response or by the contractual probe budget expiring. The per-transaction state machine is `DISPATCH → INFLIGHT → (sync response | deadline) → AMBIGUOUS → probing → {resolved terminal, GAVE_UP}`; the fallback chain executes **only** on confirmed terminals (confirmed soft decline, transport error) — never from an in-flight or ambiguous attempt. The invariants are I1 (no overlapping unconfirmed authorizations), I2 (a key is presented to exactly one processor), I3 (every late money event on a non-authorized terminal is voided or reconciled) — asserted, not assumed, by the benchmark ([S3]).
2. **The idempotency key strategy.** The key is **per (transaction, attempt)**: 128 bits, presented to exactly one processor, never reused across attempts. A new attempt is a new key; a *retry of an in-flight attempt* re-sends the **identical request with the same key** — the idempotent resend — which every processor's key namespace turns into a status query (stored response, or in-flight). The resend is the probe; it is not a new interface operation (ADR-0005 R27 holds: in Go it is the same `Authorize` call returning an `ErrInFlight` sentinel on the error channel). Production keys are CSPRNG nonces **persisted in the lease row** so a restart resumes probing with the same key; harness keys are key-derived from (seed, txn, attempt). Key namespaces are per-processor, so cross-processor double-charge prevention lives in the lease, never in the key.
3. **The classification protocol.** The outcome classes and their chain consequences are: `authorized` → terminal, sale; `declined_hard` → **chain halts** (catalog hard = a card-level verdict, never route-retried); `abandoned` → chain halts (customer-level); `declined_soft` → EV-gated chain (ADR-0002); `transport_error` → confirmed no-auth, EV-gated chain (the request never reached an issuer); `timeout` → **ambiguous: no dispatch of any kind**, probe the same (processor, key) at a fixed interval until the contractual `max_response_ms` or the resolution window, then `GAVE_UP` (reconciliation) or a confirmed terminal (chain). The state machine branches on the **class**, never on the decline code; the class is a catalog fact (ADR-0004 R34).
4. **Two clocks, one contract.** Per-attempt `ctx` deadlines (ADR-0001 R4, from `deadline_ms`) bound the *call*; a per-route-class **resolution window** (defaults: `oneoff_cnp` 30 s; `recurring_mit`/`card_on_file`/`installment` 600 s; #12 owns the config) bounds the *transaction*. The merchant-visible answer at the deadline is one of `authorized` / `declined` / **`processing`** — an ambiguous timeout is never reported as a decline. Onboarding adds two **processor-contract catalog facts**: `max_response_ms` (M — after which a conforming processor has a final, queryable state) and `key_lifetime_ms` (≥ M). A processor that cannot commit to M is onboarded as **opaque**: all its timeouts go straight to `GAVE_UP` (no chain), its late settlements to reconciliation.
5. **Idempotency is a first-class harness scenario.** The synthetic fleet honours the resend contract (re-call = status query, never a new authorization); the committed scenario `idempotency-stress-v1` carries the exposure (the workhorse arm in a 12-minute `failure_mode: timeout` outage with its `late_settlement.share` doubled, plus a `connection_refused` contrast); and the benchmark invariant is **double-charge count = 0 under the protocol**, with the naive baseline's count reported as the damage column ([S1]). A world that cannot produce a double charge cannot claim the invariant.

## Context

The ticket's scenario, in this repository's terms: a transaction is routed to charlie (the workhorse the cost table prefers for EEA/UK); charlie is *up but slow*; the 900 ms deadline passes with no response; the router retries to bravo. If the issuer was merely slow, charlie's authorization arrives at ~2.7 s **and** bravo authorizes at ~1.1 s: the customer is charged twice. The harness already models exactly this: ADR-0005's `late_settlement` channel emits a scheduled settlement for an attempt the engine gave up on ([M5]: 24.4% of the fixture's timeouts settle late — 1,178 exposures in 20,000 transactions), and `timeout` is the only one of its three failure modes "that can double-charge (#10)" — `connection_refused` and `http_503` are fast, certain, and never reach an issuer.

Three facts frame the decision:

- **Cancellation is not confirmation.** ADR-0001 chose Go partly because `context.Context` gives the deadline discipline; but cancelling the context closes the *connection*, and a processor that has received a request keeps processing it. "Up but slow" is precisely the case where the request was received. No transport-level act the router performs converts an in-flight request into a confirmed no-auth; only the processor's own stored answer can.
- **The interface was designed for this ticket; the reference driver was not.** ADR-0005's `Request` struct carries `IdempotencyKey [16]byte` with the comment *"#10: the same key on a retry of the same attempt"* and an `Attempt` field — the contract surface for a status query already exists. But the committed reference loop in `spikes/0006` breaks only on `TERMINAL = (authorized, abandoned, declined_hard, transport_error)`: after a `timeout` it **continues to the next chain arm**. The naive immediate fallback — the ticket's catastrophe — is the status quo of the reference implementation, and [S1] measures it.
- **The price of ambiguity was set, the execution side was not.** ADR-0002 excludes `timeout` from the posterior and prices it (λ_to = 45 ¢); ADR-0008 R62 binds the estimator side (a no-response attempt terminals `timeout` at the derived deadline and is *never re-labelled* as an authorization later). What neither decides is who may dispatch next, when the second dispatch is safe, and what a late **money** event does. That is this ADR: the execution side of the same ambiguity.

### What was measured (spike 0010: a reference executor on the ADR-0005 world)

The spike implements the protocol's state machine and two bounds — the **naive** fallback (the reference driver's behaviour) and the **clairvoyant** (instant truth; the upper bound on sale recovery for any protocol that does not double-charge) — on 20,000 steady-state and 60,000 stress transactions ([S1]):

| policy | saved | double charges | charges w/o sale | I1 windows | attempts/txn | margin ¢/1k |
| --- | --- | --- | --- | --- | --- | --- |
| naive (steady, 20k) | 87.61% | 163 | 122 | 819 | 1.095 | 24,631 |
| **protocol (steady, 20k)** | 85.98% | **0** | **0** | **0** | 1.059 | 24,177 |
| naive (stress, 60k) | 81.70% | **2,999** (5.00%) | 2,545 | 7,500 | 1.181 | 22,077 |
| **protocol (stress, 60k)** | 81.62% | **0** | **5** | **0** | 1.069 | 22,882 |
| clairvoyant (stress, 60k) | 85.38% | 0 | 0 | 0 | 1.114 | 24,044 |

The protocol's deficit against the clairvoyant (3.76 auth pts on stress) is exactly the lost-record mass no probe can recover; its edge over the naive is the entire integrity column — 2,999 double charges and 2,545 charges-without-sale eliminated for 0.08 auth pts of sale rate, and a *better* margin, because the probe is a free status query and the naive burns attempts.

### Considerations addressed

The ticket's five considerations map to the sections that follow: (1) the double-charge scenario → §1; (2) the idempotency key architecture → §2; (3) the retry policy (hard / soft / timeout) → §3; (4) the fallback chain execution model and late responses → §4; (5) idempotency as a first-class harness scenario → §5.

## 1. The double-charge scenario: the invariants and their measured price

**The mechanism.** A double charge needs two authorizations for one transaction. Within one processor, the key namespace prevents it: re-sending the same key returns the stored response, not a new authorization. *Across* processors it cannot be prevented at all — the namespaces are independent, and the issuer does not deduplicate a second authorization request for the same PAN (the schemes treat it as a new attempt and count it toward re-try limits). A new key is a new authorization, on whichever processor it is presented. Therefore the only place cross-processor protection can live is the **router's in-flight tracking**, keyed per (transaction, processor) and — more strongly — per transaction: the ticket's own framing ("the router must track in-flight per (transaction_id, processor) and block fallback to a different processor until the timeout is *confirmed* not suspected") is the lease, with the stronger per-transaction form, because a same-processor retry under a new key is a double charge too (I1 is per-transaction, not per-processor).

**The invariants.**
- **I1 — at most one unconfirmed authorization per transaction at any time.** A dispatch while a prior attempt is unconfirmed is the double-charge window opening.
- **I2 — a key is presented to exactly one processor**, by construction (the lease blocks the second presentation; the probe reuses the same (processor, attempt) — the memo audit in [S3] confirms every probe re-reads a record, never creates one).
- **I3 — every settlement that posts on a non-authorized terminal is handled**: voided before the money moves, or refunded/reconciled after. No silent charge without a sale.

**The measurement ([S1]).** Under the naive fallback — the reference driver's loop, executed against the stress world — 2,999 of 60,000 transactions (5.00%) carry **two authorizing pairs**: the sale closed on the second arm and the money settled on the first. A further 2,545 settled on a transaction that ended without a sale — the customer was charged for a payment the router reported as failed. Both classes are measured *in the steady world too* (163 and 122 per 20,000): the exposure is ambient, not only outagish. The 24.4%-settle-late rate of ADR-0005 [M5] re-derives to 23.9% of dispatched timeouts in the steady world ([S1] cross-check), so the exposure volume is the same order the harness was calibrated on. Under the protocol, all three columns are zero (I1, double charges, charges-without-sale) and stay zero by construction — the lease admits no dispatch while unconfirmed — with [S3] turning that into an assertion the benchmark must pass.

One subtlety the naive row hides: its *saved-sale rate* (81.70%) is **above** the protocol's (81.62%). The delta is not the naive being better at routing — it is the naive "saving" sales the protocol refuses to touch (it chains through record-lost ambiguities, correctly, since no money moves there) while the protocol, not knowing the record is lost, waits until M and gives up. The naive's extra 0.08 pts of sales are bought with the 2,999 + 2,545 integrity events; the clairvoyant — who *knows* which records are lost — takes the savings without the damage, at 85.38%. That 3.76-pt gap between protocol and clairvoyant is the information-theoretic price of confirmation, and it is the only part of the protocol's cost that the router's own parameters cannot reduce.

## 2. The idempotency key architecture

**Strategy.** `IdempotencyKey = f(transaction_id, attempt_index)`: 128 bits, one key per attempt, presented to exactly one processor, never reused. The derivation differs by world by necessity, and the difference is a design rule, not an implementation detail:

- **Production**: a CSPRNG nonce, generated at dispatch and **written into the lease row before the call goes out** (R71). The lease row carries the key because a crash mid-ambiguity must resume probing with the *same* key — a key that cannot be re-derived is a key that must be persisted, and a restart that re-derives a different one for the same in-flight attempt would turn a status query into a second authorization.
- **Harness**: key-derived from (seed, txn, attempt) via the ADR-0005 stream, so the probe is re-derivable without state and a re-run is byte-identical.

**Why the key does not carry the cross-processor protection.** The ticket states it as its second consideration: the keys are per-processor namespaces, not shared. A string presented to stripe and to adyen is, to each, an ordinary token in *its* namespace; nothing in the string format makes them refer to the same authorization. (A 128-bit value collision across namespaces is irrelevant for the same reason: the lease guarantees a key is never presented to two processors, so there is no second presentation to collide with.) The key's job is exactly one: to make a *re-send* safe — the processor deduplicates it. Everything beyond that (who may dispatch, when) is the lease. The global transaction identity that *does* cross processors is `transaction_id` itself, which rides along for correlation and for the reconciliation ledger; it is not an idempotency token anywhere.

**The resend as probe.** The status query is the idempotent resend: the same request, same key, same processor. Its answer is one of (a) the stored terminal response — the attempt's true outcome, (b) in-flight (Go: `ErrInFlight` on the error channel — no new method, no new field, R27 holds), or (c) nothing within the probe's own deadline, treated as in-flight. This is the *only* probe that works in the case that needs it: before the first response arrives, the engine holds no resource reference, so a `GET /charges/:id`-style status API cannot even be addressed. The resend needs no reference and works wherever the key works.

**Lifetime.** The key must stay queryable at least until the router has retired the ambiguity: the catalog field `key_lifetime_ms ≥ max_response_ms` (R66). Reconciliation queries against an old key after the window are a #13 ledger concern, not a routing concern.

## 3. The retry policy: hard, soft, and the third thing that is neither

The ticket's prescription — hard decline (never the same card, different processor OK), soft decline (retry same processor with delay), timeout (retry the same processor first for status, then abort or try next) — is refined by the catalog facts and the lease into the classification table the state machine executes:

| observed event | class | money state | chain consequence |
| --- | --- | --- | --- |
| `authorized` (any time, incl. probe-revealed late) | terminal | charged | none — sale (late if past the deadline; §4) |
| `declined_hard(code)` | terminal | not charged | **halts** — card-level verdict (§ below) |
| `abandoned` | terminal | not charged | **halts** — customer-level (§ below) |
| `declined_soft(code)` | terminal | not charged | EV-gated chain (ADR-0002) over the remaining arms |
| `transport_error` (refused / 5xx, fast) | terminal, **confirmed no-auth** | not charged (never reached an issuer) | EV-gated chain, immediately |
| `timeout` (deadline, no response) | **ambiguous** | unknown | **no dispatch of any kind**; probe the same (P, K) |
| probe → terminal | resolves the ambiguity | resolved | as that class's row |
| probe → in-flight, until M or the window | still ambiguous | unknown | re-probe at the interval |
| M or the window, no terminal | retired ambiguity | no charge recorded | `GAVE_UP` — reconciliation; **no chain** |

**The hard-decline adjudication.** The ticket suggests a hard decline may be retried on a *different processor*. The project's own catalog (ADR-0004 R34; the `DECLINE_CATALOG` gate in `simulator/scenarios/check.py`) defines the class the opposite way: **soft = "retryable on another route", hard = "never retry this card"** — `lost_card`, `stolen_card`, `expired_card`, `suspected_fraud`, `cvv2_failure`, `invalid_card_number`, `refer_to_issuer`… These are issuer-level verdicts about the card, not about the route: a second acquirer reaches the same issuer, pays the attempt fee, gets the same answer, and the schemes count the re-attempt toward the cardholder's re-try limits. The decision follows the catalog: **the chain halts on every hard decline**, and the ticket's line is rejected against the single source of truth. Crucially, the state machine branches on the *class*, never on the code — so if the catalog later reclassifies a code as route-specific (the live candidate is `57 transaction_not_permitted`, which real-world issuers sometimes raise per-route), the chain behaviour changes via a catalog edit and a re-pin, with no state-machine change.

**Soft and the EV test.** A soft decline is a confirmed no-auth, so the chain may proceed — gated by ADR-0002's retry test, `retry r' ⟺ θ̂(r')·win(r') − (1−θ̂(r'))·fee(r') > 0`, over the remaining arms, within the attempt cap, and only if the next attempt can fully resolve inside the window (§4). Same-processor retry (the ticket's "retry same processor with delay") is a *policy* choice the lease neither makes nor forbids: while the attempt is unconfirmed the lease blocks it; after a confirmed soft decline a same-processor retry is a legal new attempt with a new key. Which retry to prefer is #7's problem; the protocol is policy-agnostic, and the spike's static table (the ADR-0003/0004 named baseline) advances to the next arm.

**Timeout.** Implemented exactly as the ticket prescribes — *retry the same processor first for status, then abort or try next* — with "status" = the idempotent resend (§2) and "try next" available only after confirmation: a probe-revealed decline (soft: chain; hard: halt) or the contractual expiry of M on a record the processor has finalised as no-auth. What the ticket does not have a word for — the record that is *lost* (the processor kept no queryable state) — the protocol retires as `GAVE_UP`: no chain, no sale, no charge (per the fixture's mapping, a lost record carries no settlement), and a late counter. The chain proceeding from a lost record would be the naive fallback with extra steps: safe in this fixture, unsound as a contract, because the router cannot distinguish "lost" from "still processing" at any point before M — which is precisely what the probe budget buys.

## 4. The fallback chain execution model: when it runs, and what "late" means

**The state machine.** Per transaction, with the lease as the gate on every dispatch:

```
            dispatch (lease-free only; new key; attempt i)
   ┌───────────────────────────────────────────────────────────────────┐
   ▼                                                                   │
 INFLIGHT(i on P_i)                                                    │
   │  response at t ≤ t0+deadline            t0+deadline, no response  │
   ▼                                                                   ▼
 classify(response)                                       AMBIGUOUS(i on P_i)
   ├─ authorized   → AUTHORIZED (sale; late if past the   │   merchant-visible: "processing"
   │                  deadline → AUTHORIZED_LATE)         │   probe (P_i, K_i) every 500 ms,
   ├─ declined_hard / abandoned → FAILED (chain halts)    │   RTT 100 ms, budget = min(M(P_i), window)
   ├─ declined_soft / transport_error → EV test           │
   │      ├─ passes, cap & window hold → dispatch i+1 ────┘
   │      └─ else → FAILED
   └─ (probe answer is a response: same classify)
                                              min(M, window), no terminal
                                                     │
                                                     ▼
                                              GAVE_UP (reconciliation; no chain)
```

Guards on every chain dispatch: attempts < cap (2, ADR-0002's appendix); `t + deadline ≤ arrival + window` (an attempt that cannot fully resolve inside the window would buy a charge the merchant can no longer book — the sale is unsaveable, so the fee is not spent); the EV test passes. A `GAVE_UP` is terminal: the ambiguity is retired, the late counter holds the money side, and no further dispatch of this transaction is legal — *ever*.

**The two clocks.** The per-attempt `ctx` deadline (ADR-0001 R4, derived from `deadline_ms`) bounds the call and is what "timeout" measures. The **resolution window** bounds the transaction: how long the router keeps the ambiguity alive probing (and, after a confirmed terminal, chaining) before it must retire. Defaults by route class (§ decision 4): the customer-present `oneoff_cnp` flow gets 30 s of "processing"; MIT/card-on-file/installment flows, which have no customer on the page, get 600 s. The merchant-visible answer at the deadline is `authorized`, `declined` (a confirmed terminal already in hand), or `processing` — and `processing` is a first-class state, not an error: an ambiguous timeout is *never* reported as a decline (ADR-0002 R10, lifted to the transaction level). [S2](b) prices the window: above the fleet's contractual M (≤ 15 s here) it does nothing; below it, every millisecond traded for speed buys charges-without-sale (6 cws at 5 s vs 3 at 30 s on the stress world) — which is why the default sits above M and why a merchant who cannot accept a 30-s "processing" is a merchant who buys reconciliation load.

**The late-response problem, resolved by what "late" can be.** The ticket asks how a late response from the first processor is cancelled or ignored after the fallback has succeeded. In this design the question mostly dissolves, and the residue is exactly what § decision 5 tests:

- After a **confirmed** terminal, no late *response* can follow — the confirmation is the issuer's decision, recorded by the processor; a "response" arriving later is the same record, surfaced by the probe, not a new one. The probe-revealed authorization that lands after the merchant's deadline is not a late settlement either: it is the attempt's own outcome, terminal at the moment of reveal (`AUTHORIZED_LATE`), and the settlement that follows posts *under the sale* (the money backs a transaction that is authorized).
- The only genuinely late **money** event is a settlement posting on a transaction that is already terminal in a non-authorized state — reachable in the protocol only when a record finalises past the probe budget (the tail beyond M: 5 cws at 60k in [S1]) or when the window closed first. R68 handles it: **void before the money moves** (the processor holds a reference — cheap), **refund + reconciliation entry after** (the expensive path), the late counter increments, and the attempt's label is untouched — ADR-0008 R62 stands: the estimator saw a `timeout`, and it is never re-labelled.
- **Cancellation is not part of the protocol.** The `ctx` cancel at the deadline does local cleanup (the goroutine, the socket) and nothing more; the ADR-0001 R4 deadline and this ADR's lease are two halves of the same safety — one bounds the local resource, the other the money. A "cancel and chain" protocol would be the naive fallback with an extra syscall: the processor that received the request keeps processing it.

## 5. Idempotency as a first-class harness scenario

The ticket's fifth consideration is that the harness test this as a first-class scenario. Three parts:

- **The resend contract on `ProcessorClient`.** A call with a (TxnSeq, Acquirer, Attempt, IdempotencyKey) equal to one already made for that attempt is a status query: the stored terminal answer once it has finalised, else in-flight. In Go: the same `Authorize` method, with an `ErrInFlight` sentinel on the existing error channel — **no new method, no new field** (R27 holds; the interface of ADR-0005 is unchanged by this ADR). The synthetic fleet implements it by memoizing each attempt's world answer — computed once, from the same index-addressed draws as `world.attempt`, and re-read by every probe. A probe that recomputed anything differently would be a world disagreeing with itself; the steady-world cross-check in [S1] (23.9% of dispatched timeouts settle late vs [M5]'s published 24.4%, the delta being the all-arms counterfactual denominator) is the tripwire that keeps the probe's world and the scenario's world one world.
- **The scenario with the exposure.** `idempotency-stress-v1` is committed and pinned (`sha256:14273698a329`, via `python3 simulator/scenarios/check.py --pin`): charlie — the arm the cost table routes ~55% of traffic to — degrades in two stages (a 2-minute latency ramp ×3, then a 12-minute outage in `failure_mode: timeout`), with its `late_settlement.share` doubled from the fleet's 0.3 to 0.6 (the degraded processor keeps its record of more of its in-flight decisions, which is exactly the exposure a retry into a second processor has to absorb); echo takes the contrast outage (`connection_refused`, the fast certain class with the same routing consequence and none of the money consequence); the clock is the one hour around the degradation, because the lease logic is window-local and the harness scales arrivals to the declared duration. The naive baseline is *run against it and reported* — 2,999 double charges in [S1] is the damage column — because a benchmark that cannot fail is not a benchmark: a world without `late_settlement`, or a client that does not honour the resend contract, makes `dbl = 0` vacuous.
- **The invariant as a gate.** [S3]'s audit is the executable form of I1/I2/I3, and it encodes the lesson the spike's own bug history teaches: **I1 cannot be measured by a post-hoc interval scan**. The naive's first attempt is never confirmed (it is never probed), so it never appears in any confirmation interval, and the scan reports zero on the very policy that violates the invariant — a silent pass, exactly what this repository's house rules forbid. The audit therefore counts at dispatch time (a dispatch while a prior attempt is unconfirmed), which the naive fails at 7,500 and the protocol passes at 0. #17 inherits the audit: every committed benchmark run asserts `dbl = 0` and `I1 = 0` under the protocol executor and reports the naive row.

## What this binds on later tickets

- **#12 (module layout)**: the attempts manager owns the lease (a per-transaction map, single-writer per shard per ADR-0001 R5), the probe scheduler, and the void queue; `acquirer.Client` is unchanged, with the `ErrInFlight` sentinel defined next to it. `Decide` itself is unchanged — the lease lives in the execution path after the decision, so the 20 µs decision budget (ADR-0001) is untouched; [S4] prices the executor's shape (42.9 µs/txn CPython band; the lease is one map read per dispatch, the probe scheduler one heap per transaction).
- **#13 (state store)**: WAL ops `LEASE(txn, acq, key, attempt, dispatch_t, M, window)` / `RELEASE(txn, outcome)` / `GAVE_UP(txn)` / `VOID(txn, attempt, ref)` / `SETTLE(txn, attempt, at)`. The lease row is the **only** row whose loss changes money: a crash mid-ambiguity must not orphan an in-flight attempt, and startup resumes probing from the persisted key (R71) — never re-dispatches.
- **#15 (OPE)**: the attempt label is unchanged by everything this ADR does — a probe-revealed late authorization does not relabel the attempt (ADR-0008 R62); the estimator's estimand is "authorized within the deadline" and the timeout stays excluded, priced by λ_to. The propensity is logged at dispatch over the eligible set, as before. The sale-level `AUTHORIZED_LATE` metric is a business number (the dashboard's), never a posterior input.
- **#16 (dashboard)**: the panels this ADR makes first-class — the merchant-visible `processing` share (the SLO cost of the confirmation rule: 20.1% on the stress world, 6.5% steady), the lease-hold histogram by resolution class ([S3]: 330 ms median for sync authorizations, 2,000 ms for late, 7,000 ms = M for gave-up), the ambiguity mix, the late/void/reconciliation counters, and the double-charge alarm — a non-zero count is a P0 incident, not a metric.
- **#17 (benchmarks)**: the invariant gate ([S1]/[S3] as CI assertions), the committed citation `idempotency-stress-v1@sha256:14273698a329`, and the standing requirement that the naive baseline is run and its double-charge/charge-without-sale counts reported alongside any protocol claim — the damage column is what makes the zero mean something.
- **#14 (safe rollout)**: a new routing policy's shadow mode must show `dbl = 0` and `I1 = 0` over a full day before cutover; the lease is policy-independent, so the gate is the same for every policy that ever ships.
- **#11 (3DS friction)**: an abandoned challenge halts the chain (R65, the customer-level row): the customer who left the challenge cannot be re-challenged on a different processor's flow, however frictionless it is. The per-processor frictionless-rate difference is a routing lever for the *next* transaction (it is already in the context mix), not a retry within this one.

## Consequences and design rules that follow

### Easier

- The chain logic is *simpler* than the naive's, not more: one guard ("confirmed terminal?") replaces a guess ("was that a timeout?"), and the chain's dispatch conditions (cap, window, EV) are the ADR-0002 ones, unchanged.
- The synchronous path gains exactly one answer type (`processing`) and nothing else; a timeout is no longer a routing decision at all — it is a state.
- Probes are free status queries: no attempt fee, no attempt-cap slot, no posterior update, no reward — the confirmation machinery costs the engine nothing beyond the lease and a timer.

### Harder

- Asynchronous money state must be **durable and resumable**: the lease survives a crash mid-ambiguity, and a restart that forgets it re-opens the double-charge window on its own (R71 is the whole point of persisting the key, not just the fact).
- The resolution window is a per-route-class config that must be reconciled with merchant UX and with the fleet's contractual M — a mis-set window is a leak of either SLO (too long) or cws (too short; [S2](b)).
- The **opaque** class is a second onboarding track: a processor that cannot commit to M routes its timeouts straight to reconciliation, and the merchant-facing answer for its traffic degrades from "we will confirm" to "we will tell you" — the catalog must carry the class, and onboarding must verify the contract rather than assume it.
- The benchmark must carry the damage column permanently, and the dashboard must make a zero-meaningful alarm (double charge) first-class: both are costs of a safety property that only exists if someone is watching for its failure.

### Design rules added

- **R63** — **The lease (I1):** at most one unconfirmed authorization exists per transaction at any time. A dispatch is legal only from a lease-free state; the lease releases only on a confirmed terminal response or on the probe budget `min(M, window)` expiring. Same-processor retries under a new key are blocked by the same rule while unconfirmed — I1 is per-transaction, not per-processor.
- **R64** — **The key (I2):** the idempotency key is per (transaction, attempt), 128 bits, presented to exactly one processor, never reused across attempts. A retry of an in-flight attempt re-sends the identical request with the same key (the idempotent resend; in-flight is reported on the error channel, `ErrInFlight` — no new interface surface). Production keys are CSPRNG nonces persisted in the lease row before dispatch (crash resume, R71); harness keys are key-derived from (seed, txn, attempt). Key namespaces are per-processor: the key makes a *re-send* safe; the lease makes the *second dispatch* safe.
- **R65** — **Confirmed-terminal fallback:** the chain executes only on confirmed terminals. `declined_hard` and `abandoned` halt it (card-level and customer-level verdicts); `declined_soft`, `transport_error`, and a probe-revealed no-auth proceed EV-gated (ADR-0002) over the remaining arms, within the attempt cap, and only if `t + deadline ≤ arrival + window`. `timeout` — the only ambiguous outcome — never authorizes a dispatch; it authorizes only the probe of the same (processor, key). The state machine branches on the decline *class* (a catalog fact, ADR-0004 R34), never on the code.
- **R66** — **The processor contract:** onboarding records two catalog facts per processor: `max_response_ms` (M — after which a conforming processor has a final, queryable state for every request it received) and `key_lifetime_ms` (≥ M). A processor that cannot commit to M is onboarded as **opaque**: all its timeouts terminal `GAVE_UP` (no chain) and its late settlements go to reconciliation. M and the class are catalog facts pinned by `catalog_hash`, like cost and capability.
- **R67** — **Two clocks, one answer:** per-attempt `ctx` deadlines (ADR-0001 R4) bound the call; the per-route-class resolution window (defaults `oneoff_cnp` 30 s; `recurring_mit`/`card_on_file`/`installment` 600 s; #12 owns the config) bounds the transaction and the probe budget. The merchant-visible answer at the deadline is `authorized`, `declined`, or `processing` — an ambiguous timeout is never reported as a decline. The window sits above the fleet's M unless the merchant explicitly accepts the cws price of [S2](b).
- **R68** — **Late money events:** a settlement posting on a transaction terminal in a non-authorized state is handled, never absorbed: void before the money moves (a reference exists), refund + reconciliation entry after; the late counter increments; the attempt label is never re-written (ADR-0008 R62 — the estimator saw `timeout` and keeps it).
- **R69** — **Probe discipline:** the status probe re-sends at a fixed interval (default 500 ms), each with its own deadline (default 1 s), until the probe budget `min(M, window)`. Probes are free: no attempt fee, no attempt-cap slot, no posterior update, no reward. [S2](a) is the evidence for the defaults' role: the interval moves probe volume (77,834 → 15,964 over 250 → 2,000 ms) and resolution speed, and does not move the outcome.
- **R70** — **The benchmark invariant:** every committed benchmark run executes the protocol, asserts `double_charge = 0` and `I1 = 0`, and reports the naive baseline's `double_charge` / `charge_without_sale` counts as the damage column. A scenario that cannot produce a double charge (no `late_settlement`, or a client that does not honour the resend contract) cannot carry the claim. The committed stress scenario is `idempotency-stress-v1@sha256:14273698a329`.
- **R71** — **Crash semantics:** the lease row (txn, acq, key, attempt, dispatch_t, M, window) is WAL-durable at dispatch, **including the key** — a restart resumes probing with the persisted key and must never re-dispatch an ambiguous transaction. The lease row is the only state whose loss changes money; all other attempt state is reconstructible or replayable.

### Reopen triggers

1. **Cross-processor dedup becomes contractually available** — issuer-level network-token idempotency, or a scheme-level guarantee that a duplicate authorization for the same (card, transaction) is rejected — reopens R63: the lease can relax to per-processor and "chain during ambiguity" re-enters the design space, since the issuer (not the router) carries the double-charge risk.
2. **Real reconciliation data shows a confirmable processor losing records** — sustained `P(record lost | timeout, approved) > 10%`, measured as late-counter rate against probe-resolution rate — reopens R66: the contract is being violated; the processor is demoted to opaque or its M re-derived, and the onboarding verification is tightened.
3. **The probe stops being cheap** — a processor's status path p99 exceeds the probe budget (the [S2](a) flatness collapses: outcome starts to depend on the interval) — reopens R69: the probe discipline is re-derived, and if the probe's cost approaches λ_to per ambiguity, the EV of probe-versus-early-`GAVE_UP` is recomputed per processor.
4. **Merchants standardize a short "processing" TTL** below the fleet's M — reopens R67: per-merchant window overrides become config, and [S2](b)'s cws column becomes a merchant-facing SLA number (speed bought with reconciliation load, priced per millisecond).
5. **The double charge gets a real price** — refund + dispute + chargeback + brand cost, measured, at more than 10× or less than 1/10 of λ_to — reopens the pricing of ambiguity end-to-end: ADR-0002 R12's λ_to and this ADR's windows move together, because both are the same quantity (the cost of not knowing) expressed in different units.

## Alternatives considered

1. **Immediate fallback with a new key (the naive).** Retry the next chain arm at the deadline, no lease, no probe. Rejected by measurement: 2,999 double charges and 2,545 charges-without-sale in 60,000 transactions (5.0% of traffic doubly charged) on the stress world — and 163 + 122 per 20,000 in the *steady* world — for a net +0.08 auth pts of sale rate, the entire "advantage" of which is the double charges. It is also what the committed reference driver does today; adopting it as the protocol would make the harness's most instructive failure mode the production design.
2. **One shared idempotency key across processors.** Present the same 128-bit string to stripe and to adyen and let the key carry the cross-processor protection. Rejected: the namespaces are per-processor (the ticket's own second consideration), so a shared string deduplicates nothing outside each processor; and with the lease in place the key is never presented to two processors anyway, so the shared format buys nothing even against value collisions. The key is a per-processor dedup token; the global identity that crosses processors is `transaction_id`, used for correlation and the reconciliation ledger, not for idempotency.
3. **A central "was this authorized?" oracle** (an issuer- or scheme-level status service the router queries before chaining). Rejected: no such contract exists; the issuer does not deduplicate; and even a queryable *pending* state has the same ambiguity it would replace (pending ≠ confirmed). It also adds a second system on the money path whose own outage mode is undefined — a new way to be wrong, in exchange for information the processor already has behind its key.
4. **A per-processor status API as the probe** (e.g. `GET /v1/charges/:id`) instead of the idempotent resend. Some processors have one; none of them have it *before the first response* — the resource reference does not exist yet, which is exactly the timeout case. The resend works everywhere the key works, needs no reference, and its two-state answer (stored response | in-flight) is the confirmation itself. A status API is an acceptable optimization on top of R64 where it exists — not the contract.
5. **Cancel the in-flight request, then chain.** Close the connection (or send the processor's cancel) at the deadline to make the fallback safe. Rejected: cancellation is transport-level; a processor that received the request keeps processing it — "up but slow" *is* the received-but-processing case — and no cancel response confirms the no-auth any better than silence does. The `ctx` cancel remains where ADR-0001 R4 put it: local cleanup.
6. **Wait synchronously until confirmation** (hold the merchant call until the probe resolves, return the final answer at `min(M, …)`). Rejected: the merchant's SLO is the deadline; holding a 900 ms API call for 3–15 s converts a latency budget into a checkout timeout. The async window (R67) buys the same safety with a first-class `processing` state instead. [S2](b)'s 5-second row is the price list for merchants who insist on the synchronous form.
7. **Same-processor retry with a new key on timeout.** Keep the chain on one processor (the ticket's "retry the same processor") but as a *new* request. Rejected as a substitute for the probe: a new key is a new authorization in the same namespace — if the first request is still processing, the second can double-charge *within* the processor. The safe same-processor retry is the resend (same key), which is the probe; the unsafe one is what R63/R64 exist to block.
