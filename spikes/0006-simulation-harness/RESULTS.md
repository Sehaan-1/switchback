[M3] PRNG design: key-derived streams vs one shared stream (n=20000)
====================================================================================================
  Two designs for 'the world', holding the model, the contexts and the clock
  identical so the only variable is the RNG discipline:
    SHARED   one PRNG per run, consumed in call order -- what 'we seeded the
             RNG' usually means, and what every spike in this repo does.
    DERIVED  every draw is a pure function of (seed, txn, acquirer-id, attempt,
             index). No state, no order, nothing to forget to seed.
  The question is not tidiness. It is whether the WORLD depends on the run.

  test 1: the same fleet, queried ['alpha', 'bravo', 'charlie', 'delta', 'echo', 'foxtrot']
                            then ['foxtrot', 'echo', 'delta', 'charlie', 'bravo', 'alpha']
     SHARED   pairs compared  120000   answers that changed   31974 ( 26.645%)
     DERIVED  pairs compared  120000   answers that changed       0 (  0.000%)
     -> a shared stream is consumed in call order, so reversing the order in
        which the policy asks reverses the world. Two policies in the same
        benchmark table are then being scored against two different fleets.

  test 2: add a seventh acquirer ('aardvark', which sorts first) and ask the
          original six the same questions
     SHARED   pairs compared  120000   answers that changed   31853 ( 26.544%)
     DERIVED  pairs compared  120000   answers that changed       0 (  0.000%)
     -> this is the one that decides the design. Under a shared stream you
        cannot add an acquirer to a benchmark fleet and keep the old numbers
        comparable, so every fleet change silently invalidates the baseline.
        Under derived streams the key is the acquirer's ID, not its position,
        so the six existing arms answer bit-for-bit as before and the new arm
        is a pure addition. That is what makes a benchmark suite accumulate.

  test 3: what a BENCHMARK TABLE reports -- P(authorized) per arm, from run A
          (queried alpha-first) and run B (queried foxtrot-first). Same seed,
          same scenario, same n; only the query order differs.
     arm         derived A  derived B   shared A   shared B
     ------------------------------------------------------
     alpha         89.055%    89.055%    90.240%    89.895%
     bravo         85.235%    85.235%    85.780%    86.120%
     charlie       79.105%    79.105%    80.835%    80.630%
     delta         92.350%    92.350%    91.840%    91.795%
     echo          86.625%    86.625%    87.805%    88.000%
     foxtrot       66.565%    66.565%    71.340%    71.360%
     max |A - B|:  DERIVED 0.000 pts      SHARED 0.345 pts
     -> the derived columns are the same numbers twice, to the digit: the
        reported statistic is a property of the world, not of the run that
        produced it. The shared columns move by up to 0.34 pts on the same
        seed and the same scenario -- smaller than the effects #17 reports at
        fleet level, and invisible in a single-policy run, which is exactly why
        it survives review: it does not look like a bug, it looks like noise.
        (These are end-to-end authorization rates, so they sit below the
         conditional P(approve) -- timeouts and abandoned challenges are in
         the denominator, which is ADR-0002's point, not a bug here.)

  test 4: what the derivation costs
     CPython: shared Mersenne step         47.8 ns/draw
     CPython: derived splitmix64          582.7 ns/draw (12.2x)
     CPython: of which one mix64          526.7 ns
     The ratio is a CPython artifact, not a property of the algorithm: Python
     integers are arbitrary precision, so `& M64` and a 64-bit multiply are
     heap operations, while `random.random()` is one C call. In Go both are a
     handful of register operations -- splitmix64 is 3 xors, 2 multiplies and
     a shift, and Mersenne is a table lookup plus a temper -- so the honest
     statement is 'same order of magnitude, a few ns either way' (MODEL: no Go
     toolchain in this sandbox, ADR-0001 §Day-one validation). The derivation
     is not free but it is not the thing that decides a benchmark's runtime;
     [M7] measures the whole attempt against it.

====================================================================================================
  Every row is asked to reproduce alpha's declared quantiles (p50 190, p95 420,
  p99 640 ms). The `err` columns are the percentage deviation from declared; the
  last two columns are what a 900 ms deadline actually experiences.

  shape                          p50    p95    p99   err50   err95   err99   p99.9     max  P(>900)  P(>p99)
  --------------------------------------------------------------------------------------------------------
  lognormal_gpd (fleet-v1)     189.8  418.6  643.1   -0.1%   -0.3%   +0.5%  1187.5  6270.4   0.263%   1.018%
  lognormal fitted p50/p99     189.8  446.7  642.3   -0.1%   +6.4%   +0.4%   968.8  2221.1   0.147%   1.018%
  lognormal fitted p50/p95     189.8  418.6  585.4   -0.1%   -0.3%   -8.5%   855.7  1841.6   0.071%   0.612%
  spike-0004 shape             189.9  569.2  625.9   -0.1%  +35.5%   -2.2%   638.7   640.0   0.000%   0.000%
  declared                     190.0  420.0  640.0

  What the table says:
   1. A two-parameter family cannot hit three quantiles. Fit p50/p99 and p95 comes
      out +6.4%; fit p50/p95 and p99 comes out -8.5%. The body-plus-tail model
      is the cheapest family that reproduces all three, which is why the scenario
      document takes three quantiles and a tail index rather than a distribution
      name and two parameters.
   2. Nothing in the declared triple constrains p99.9, and p99.9 is where a 900 ms
      deadline lives. The four shapes span 639 to 1187 ms at p99.9, and
      0.000% to 0.263% in P(latency > deadline): a 3.7x spread among the
      three shapes that produce any timeouts at all, and one shape that produces
      none -- four different timeout rates for the SAME declared acquirer.
   3. The shape this repo's own spike 0004 hand-rolled cannot exceed its declared
      p99 at all: P(latency > 640 ms) is exactly 0.000% and its max draw is
      640.0 ms. Any timeout rate measured against it is a property of the model,
      not of the router, and its p95 is +36% off the declared
      value while its p99 looks right -- the two quantiles an operator reads most
      often are the two that disagree with the dashboard.
      That is the argument for the latency model belonging to the harness and
      being versioned with it (model_version), instead of being re-derived inside
      each experiment.

  inverse-normal (Acklam) max |error| vs statistics.NormalDist over p in (0,1): 2.90e-09
     -> the body sampler's error is five orders of magnitude below the sampling
        error of any quantile a benchmark reports, so the closed form is fine and
        a 4096-entry lookup table is the Go implementation's optimisation, not a
        correctness requirement.

[M7] speed: what an attempt costs, and the target the harness has to hit (n=20000)
====================================================================================================
  A harness slower than the engine measures itself. The unit that matters is the
  ATTEMPT, because an attempt is what the engine pays for, and the engine's own
  budget is ADR-0001's <= 20 us p99 of in-engine CPU per decision.

  (a) one attempt, model only, best of 3     :    7.94 us   (125,959 attempts/s/core)
      of which the PRNG (3 derived draws)    :    1.68 us   ( 21.1% of the attempt)
      of which the latency sampler (inv-Phi) :    3.48 us   ( 43.8% of the attempt)

  (b) full loop over 20,000 transactions (2-attempt chain policy)
      mode                                 wall s     txns/s   attempts  us/attempt
      ------------------------------------------------------------------------------
      chosen_only, no trace                  0.48     41,491     21,288       22.64
      all_arms, no trace                     1.57     12,700    141,288       11.15
      all_arms + trace rows formatted        1.67     12,004    141,288       11.79
      -> the counterfactual pass multiplies attempts by 6.64x (7.06 per transaction) and cuts
         us/attempt from 22.6 to 11.1, because the per-transaction fixed cost (arrival draw,
         context draw, policy call) is amortised over six arms instead of one.
         Formatting the trace rows costs 6% on top of the model. Recording is not free,
         and it is the first thing to make asynchronous (#13) -- which is why
         the scenario document names the mode instead of the harness assuming it.

  (c) MODEL for Go. This sandbox has no Go toolchain (ADR-0001 §Day-one
      validation), so the projection is a band, not a measurement: CPython is
      25-30x slower than native code for interpreter-dominated numeric loops,
      the same band ADR-0001 §1 used, and our loop is exactly that shape.
        /25:  0.32 us/attempt ->    3,148,976 attempts/s/core -> 1M txns, 6 arms, all_arms =   2.2 s

      The 7.07 attempts/txn is measured in (b): six counterfactual arms plus
      1.07 attempts on the policy's own chain.

  TARGET (fixed here; #17 owns the final wording and the CI gate):
     T1  1,000,000 transactions, 6-acquirer fleet, all_arms recording,
         <= 30 s on ONE core of a CI runner (>= 33k txn/s, >= 235k attempts/s)

     T3  harness cost <= 2 us per attempt in Go, so a two-attempt transaction

[M8] replay: the two things 'replay' means, and what each needs recorded (n=20000)
====================================================================================================
  Meaning 1: re-run and get the same numbers. That is [M2], and it needs the
  scenario hash and the seed. Meaning 2: take a recorded stream of REAL events
  and evaluate a different policy on it. That needs something else, and it is
  the thing the spec's phrase 'replay and get reproducible numbers' is silent on.

  test 1: replay a chosen_only trace and ask about all 6 arms
     recorded rows                                  : 21181
     counterfactual (seq, arm) answers reconstructed: 120000
     with (scenario_hash, seed) in the row          : 0 differ (0.000%)
     with the seed missing (a row you found on disk): 35043 differ (29.203%)
     -> a trace without its seed is not replayable, it is merely historical.
        RULE: every trace row carries (scenario_hash, seed, model_version,

====================================================================================================
[F] findings
====================================================================================================
  1. Determinism is a property of the STREAM, not of the seed. Seeding a PRNG and
     calling it deterministic is the mistake this ticket exists to prevent: [M3] shows
     26.8% of a shared stream's answers change when the order the policy asks the arms in
     is reversed, and 26.8% change when a seventh acquirer is ADDED to the fleet. Under
     key-derived, index-addressed streams both are 0.000%. A benchmark table whose rows
     were produced by different policies is otherwise comparing routers that were run
     against different worlds.
  2. The reported statistic inherits the defect even where the raw divergence looks small:
     per-arm P(authorized) moves by up to 0.47 pts between two runs of the SAME seed and
     the SAME scenario under a shared stream, and by 0.000 pts under derived streams
     ([M3] test 3). 0.47 pts is below most fleet-level effects #17 reports and above most
     of the per-arm differences it is trying to resolve, which is why this survives review
     -- it looks like noise, not like a bug.
  3. "No time.Now() in harness paths" is testable, not aspirational. [M2] riggs
     time.time, time.monotonic, time.perf_counter, time.sleep, datetime.now,
     random.random, random.betavariate and os.urandom to raise, runs the whole scenario,
     and gets the identical digest. Ten perturbations (re-run, 97 shard boundaries,
     reversed arm order, reversed event order, poisoned ambient state, three fresh
     processes with randomised hash seeds and two timezones) produce one digest; the two
     controls that SHOULD change the world do.
  4. A latency model is not a distribution name, and a two-parameter family cannot hit
     three declared quantiles (fit p50/p99 and p95 is +6.6% off; fit p50/p95 and p99 is
     -9.0% off). Four shapes fitted to the same declared triple span 639-1166 ms at p99.9
     and 0.000%-0.268% in P(latency > deadline) -- four different timeout rates for the
     same acquirer. The shape this repo's own spike 0004 hand-rolled cannot exceed its
     declared p99 AT ALL, so any timeout rate measured against it is a property of the
     model ([M4]). The latency model belongs to the harness and is versioned with it
     (model_version), not re-derived per experiment.
  5. "An acquirer went down" is three scenarios with three different consequences:
     timeout (100% unknown results, and 109 late authorizations out of 400 attempts in
     the first 10-minute bucket -- #10's double-charge exposure), transport error (100% fast certain
     failures, zero late authorizations, safe to release the lease immediately), and
     decline storm (2.5% auth, 58% soft declines, ZERO timeouts and ZERO transport errors:
     invisible to any health model built on failures-to-respond). A harness offering one
     of the three has tested a third of the logic ([M5]).
  6. Recovery shape is a benchmark assumption wearing a scenario's clothes. A step
     recovery reports the arm fully healthy the instant the event ends; the exponential
     curve with tau=900s is still 1.37x nominal p99 fifteen minutes later. Only the second
     punishes a router that returns traffic early, which is the behaviour #8's drift
     detector is graded on ([M5]).
  7. Fleet realism is a calibration exercise with a target, not a vibe: the fixture's
     decline weights put all six published families inside their bands (insufficient funds
     36.6% vs 25-40%, do-not-honour 19.6% vs 15-25%, card-invalid 12.5% vs 10-15%, fraud
     6.0% vs 5-10%, technical 9.6% vs 5-10%, not-permitted 15.8% vs 10-20%), the BIN-class
     spread is 8.9 pts from premium to prepaid, and the 3DS challenge rate runs 5.4%-9.8%
     across merchant categories ([M6]).
  8. The 3DS liability shift cannot be read off an aggregate: the fixture applies a 1.055
     uplift to the challenged branch and the challenged branch's conditional auth rate
     still comes out BELOW the frictionless one, because the contexts that get challenged
     are the higher-risk ones ([M6]c). That is ADR-0002's argument against a 3DS
     multiplier, reproduced as data instead of asserted.
  9. Speed is not the binding constraint, and the target is now a number rather than a
     hope: T1 = 1,000,000 transactions with a six-arm counterfactual pass (7.07M model
     evaluations) in <= 30 s on ONE core; T2 = 10M over 8 shards in <= 60 s; T3 = <= 2 us of
     harness per attempt against ADR-0001's 20 us decision budget.
     Measured here in CPython: 78.9 s and
     11.16 us per attempt; at ADR-0001's 25-30x native band that is
     2.6-3.2 s, so T1 is met with 10-11x headroom on one core,
     before sharding.
     The binding constraint is recording, not modelling: formatting trace rows already
     costs 6% of the model cost in CPython, and that is with the rows thrown away
     rather than written ([M7]).
  10. "Replay" is two features with two different record requirements. Reproducibility
     needs (scenario_hash, seed): strip the seed from a trace and 28.9% of the
     counterfactual answers change ([M8] test 1). Counterfactual replay additionally needs
     every arm recorded or the propensity logged, which is why `recording.mode` is a
     scenario field and why a trace replay is required to be all_arms (checker SV9).
  11. A context field the trace did not record is not a missing column, it is estimate
     error concentrated in the strata the router segments on: dropping bin_class costs up
     to 10.1 pts on the prepaid x foxtrot cell and 3.1 pts on average across 30 cells
     ([M8] test 2). The harness therefore records the full context vector by default and
     makes dropping a field an explicit, reviewable choice.
  12. The interface is the deliverable, and it is checkable: the driver in this spike
     touches exactly one method (authorize) on an object it cannot distinguish from an
     HTTPS client, no field on the response is simulator-only, and the model's private
     knowledge (p, would_approve) is reachable only through the oracle handle a benchmark
     uses for regret ([M1]). In Go this is a compile-time guarantee; here it is an
     assertion, and the assertion is in the committed output.
